# 주차대행 취소분 모니터링 계획서 (spec.md)

상태: 승인 대기 / 작성: Plan 서브에이전트 / 구현 코드는 이 문서에 포함하지 않음

## 1. 목적과 범위

예약 희망 기간 2026-10-24 ~ 2026-11-02 중, 마감된 날짜에 취소로 자리가 나면(마감 -> 예약 가능) 텔레그램으로 알린다.

| 구분 | 내용 |
|---|---|
| 이번 범위 | 출발일 2026-10-24, 일반(BASIC)만 확인 |
| 범위 밖 (향후 확장) | 도착일 2026-11-02 조회, 프리미엄(PREMIUM) 조회 |
| 하지 않는 것 | 자동 예약 (인증코드 필요, 알림만 제공) |

대상: https://valet.amanopark.co.kr/booking (Nuxt SPA, 마감 여부는 API 호출로 판단)

## 2. 동작 방식

1. GitHub Actions가 5분마다 `monitor.py` 실행
2. `GET https://api.amanopark.co.kr/api/web/setting/booking/check` 호출
   - 파라미터: `date=2026-10-24`, `type=BASIC`, `dateType=departing_at` (생략 가능성 있어 첫 실행 때 둘 다 확인)
   - 응답은 `{data: true|false}`로 **추정** (true = 예약 가능). 미검증 상태
3. 이전 상태(마감/가능)와 비교
4. 마감 -> 가능으로 바뀌면 텔레그램 알림 (예약 페이지 링크 포함)
5. 현재 상태를 저장하고 종료

참고: 마감 시 프론트 문구는 "당일 주차대행 접수가능 대수가 초과되어 예약이 불가합니다"

## 3. 파일 구조

```
tools/valet-monitor/
  spec.md          # 이 계획서
  monitor.py       # 조회, 비교, 알림 (표준 라이브러리 위주, 외부 의존성 최소화)
.github/workflows/
  valet-monitor.yml  # cron + workflow_dispatch
```

블로그 파일과 `apps/`는 수정하지 않는다. (참고: `.github/`는 저장소 루트에 있어야 Actions가 인식하므로 승인 시 이 경로 생성을 함께 허락받는다.)

## 4. 상태 저장 방법 (중복 알림 방지)

Actions는 실행 간 상태가 없으므로 아래 3안을 비교했다.

| 안 | 장점 | 단점 |
|---|---|---|
| A. actions/cache | 커밋 없음, 저장소 깨끗, 설정 간단 | 캐시는 불변(키를 매번 새로 만들고 restore-keys로 복원해야 함), 7일 미접근 시 삭제, 유실 시 알림 1회 중복 가능 |
| B. 상태 파일 커밋 | 상태가 눈에 보임, 커밋이 활동으로 간주되어 60일 비활성화 완화 | 상태 변경마다 커밋(이력 오염), `contents: write` 권한 필요, 푸시 충돌 가능 |
| C. 가능 상태면 매번 알림 | 상태 저장 불필요, 가장 단순 | 자리가 열려 있는 동안 5분마다 알림 폭주, 알림 피로 |

**추천: A (actions/cache).** 이유: 상태가 "마감/가능" 한 값뿐이라 캐시로 충분하고, 권한 상승과 커밋 노이즈가 없다. 캐시 유실의 최악 결과는 알림 1회 중복이라 허용 가능하다. 키는 `valet-state-${{ github.run_id }}`로 저장하고 `restore-keys: valet-state-`로 가장 최근 것을 복원한다. 60일 비활성화 문제는 B가 아닌 별도 대응(6장 리스크)으로 다룬다.

알림 규칙: 마감 -> 가능 전환 시 1회 알림. 가능 상태 유지 중에는 재알림 없음. 가능 -> 마감 복귀 시 상태만 갱신(알림 없음). 최초 실행(상태 없음)에서 이미 가능이면 알림.

## 5. 텔레그램 설정

1. 텔레그램에서 `@BotFather` -> `/newbot` -> 봇 토큰 발급
2. 만든 봇에게 아무 메시지 전송 후 `https://api.telegram.org/bot<TOKEN>/getUpdates`에서 `chat.id` 확인
3. 저장소 Settings -> Secrets and variables -> Actions에 등록
   - `TELEGRAM_BOT_TOKEN`
   - `TELEGRAM_CHAT_ID`
4. 보안: 토큰은 환경변수로만 읽고 코드, 로그, 에러 메시지, URL 출력에 절대 노출하지 않는다 (예외 메시지에서 URL 마스킹). 위 `getUpdates` 확인은 사용자 로컬에서만 수행한다.

## 6. 에러 처리

| 상황 | 처리 |
|---|---|
| 네트워크 오류/5xx/타임아웃 | 타임아웃 10초, 최대 3회 재시도(지수 백오프), 그래도 실패하면 실패 카운트 증가 |
| 4xx(차단, 변경) | 재시도 없이 실패 처리, 로그에 상태코드만 기록 |
| 응답 형식 변경 (`data`가 bool이 아님 등) | **알림하지 않음.** 경고 로그 + 원문 일부 기록, 실패 카운트 증가 (오탐 방지) |
| 연속 실패 | 12회 연속(약 1시간) 실패 시 텔레그램 "모니터링 이상" 경고 1회, 복구 시 복구 알림 1회. 카운트는 상태 캐시에 함께 저장 |
| 텔레그램 전송 실패 | 재시도 후에도 실패하면 job을 실패 처리(GitHub 실패 메일로 인지), 상태는 갱신하지 않아 다음 실행에서 재알림 |

## 7. 리스크와 제약

- **GitHub cron 지연/누락**: 스케줄은 부하 시 수 분~수십 분 지연되거나 건너뛸 수 있다. 5분 간격은 "대략"이며 짧게 열렸다 닫히는 자리는 놓칠 수 있다.
- **60일 무활동 비활성화**: 저장소에 60일간 활동이 없으면 스케줄이 자동 비활성화된다. 이번 기간(10/24 이전)은 해당 없으나 장기 운용 시 Actions 탭에서 재활성화 필요.
- **비공식 API**: 문서화되지 않은 내부 API라 예고 없이 변경/차단될 수 있다. 응답 형식은 추정이며 현재 개발 환경에서는 api.amanopark.co.kr 접속이 프록시에 막혀 직접 검증하지 못했다.
- **요청 빈도 예절**: 5분당 1회(하루 약 288회)로 제한, User-Agent 명시, 동시 실행 방지(`concurrency` 설정).
- **이용약관**: 자동 조회가 사이트 이용약관에 저촉되지 않는지 사용자가 확인할 것을 권고한다.
- **모니터링 종료**: 예약 성공 또는 10/24 경과 후 workflow를 비활성화한다 (자동 종료 로직은 이번 범위 밖).

## 8. 검증 계획

1. **응답 형식 검증(최우선)**: workflow_dispatch로 첫 실행 시 "검증 모드"로 원문 응답(상태코드, 본문 앞부분)을 로그에 출력하고, `dateType` 포함/생략 두 경우를 비교한다. 토큰은 출력 금지.
2. 브라우저에서 해당 날짜가 실제 마감인지 눈으로 대조해 true/false 의미(true = 가능)를 확정한다.
3. **테스트 알림**: 입력값으로 강제 알림을 보내 텔레그램 수신과 Secrets 설정을 확인한다.
4. **상태 전이 테스트**: 캐시 상태를 인위적으로 "마감"으로 둔 뒤 "가능" 응답을 모의하여 알림 1회, 재실행 시 무알림을 확인한다.
5. 에러 경로: 잘못된 URL/응답 모의로 경고 로그와 연속 실패 알림 동작을 확인한다.
6. 스케줄 실행: 수동 검증 후 cron 실행이 실제로 도는지 1~2시간 관찰한다.
